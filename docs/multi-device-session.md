# 电脑与手机「互相顶掉登录」：结论与验证清单

> 2026-10-27 定位。对应 1.0.8 的修复。这篇是给**复现与验收**用的，不是实现说明
> （实现说明在代码注释里：`services/session/AuthTokenStore.ets`、`services/auth/SessionVerdict.ets`）。

## 一句话结论

**不是**服务端做了"单会话/单设备限制"。Discourse 正常配置下每个客户端各有一枚独立令牌，
互不影响（`app/models/user_auth_token.rb` 的 `MAX_SESSION_COUNT = 60`，且只在登录时淘汰最旧的）。

真正的链路是：App 揣着一枚**已被服务端作废的认证令牌**反复重放，而这会打满上游**按 IP** 计的
限流锁，把同一网络里另一台设备的**有效**令牌一起拖死。

## 机制（逐跳）

1. `_t` 约每 10 分钟在服务端轮换一次。App 为了对抗"ArkWeb 冷启动恢复不出 `_t`"，把凭据备份进
   系统密钥库并在每次冷启动写回 cookie 仓（这是 1.0.6 的会话韧性修复，方向没错）。
2. 一旦这枚令牌在服务端已作废（被退出/被轮换出窗口/账号侧变更），上游在
   `lib/auth/default_current_user_provider.rb` 里置 `BAD_TOKEN`，并由 `lib/hijack.rb:95` 与
   `lib/middleware/request_tracker.rb:410` 回响应头 `Discourse-Logged-Out: 1`，同时 Set-Cookie
   删掉浏览器侧那份。**但密钥库里的备份删不掉** —— 下次冷启动又灌回去，重放。
3. 同一文件里那把限流锁：`RateLimiter.new(nil, "cookie_auth_#{request.ip}", 10, 1.minute)`。
   key 含 **IP**，且只有"带了认证 cookie 却没认出人"才计数。App 刷满它之后，
   **同一 Wi-Fi 下电脑浏览器的请求会撞上同一道闸** → 那枚有效令牌也被判 BAD_TOKEN 并删 cookie。
4. 于是表现成双向对称的"互踢"：谁先重放死令牌，另一个人掉线。

## 修了什么

- 网络层捕获 `Discourse-Logged-Out`（GET 与带 CSRF 的写请求两条通道都取）。
- 404 + 该头 = 服务端正面证据 → 直接确认登出（不再依赖"cookie 探测"这种真机上会说谎的旁证）。
- 确认作废后：**无条件清掉 cookie 仓里那一枚** + 把该枚的**不可逆短指纹**钉进名单，
  此后恢复/备份两条路都绕开它；新会话建立时名单自动解除。
- 用户主动退出走同一套隔离（补掉"异步销毁没跑完 → 已注销会话被写回来"的洞）。
- 凭据落盘/写回日志与「网络快照」都带上短指纹，能分辨"还是那一枚"与"已经换了一枚"。

## 明天验收：三件事

**A. 先看一眼基线（装机后、复现前）**
设置 → 诊断日志 → **网络快照**，抄下这两行：

```
认证令牌 jar=<8位> 备份=<8位> cookie仓长度=<数字>
最近一次被服务端拒签：<时间> 令牌=<8位>
```

**B. 复现并回看**
1. 手机登录 App（正常浏览几分钟，让 `_t` 至少轮换一次）；
2. 电脑浏览器登录同一账号；
3. 回手机，看是否还登录；若掉了，立刻再点一次「网络快照」。

判读：
- 「最近一次被服务端拒签」的时间**与电脑登录时刻接近** → 证实是那一次登录把我们顶掉的，
  且新版会隔离该枚、不再重放，同网络的另一端不会再被连累。
- `jar` 与 `backup` **不同**且反复出现 → 我们仍在重放旧令牌（修复未覆盖到某条路径），把日志导出给我。
- 两端**长时间都不掉** → 问题消失。

**C. 顺带确认一个前提**（可选但很有价值）
网页版「偏好设置 → 安全」里能看到已登录设备列表。若手机 App 与电脑浏览器各自成一行且**同时在线**，
说明站点没有单会话限制，与上面的结论一致。

## 仍未证实的（不下结论）

- 无法读取站点的 `log_out_strict` / `maximum_session_age` 等设置（需管理员）。
  若站点开了 `log_out_strict`，则"任一端点退出登录会把所有设备一起下线"是**服务端语义**，
  客户端改不动 —— 但那种情况下"登录"仍不该互踢，与本条现象不同，可据 B 的判读区分。
- 系统分享、长时任务（音频后台播放）、桌面快捷入口等属新功能，不在本文件范围。
